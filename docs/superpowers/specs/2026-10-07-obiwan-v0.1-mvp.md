# Jarvis Obi-Wan — MVP v0.1

> **The purpose of this document is to cause code to be written.**

Obi-Wan v0.1 is the smallest useful implementation of the shared knowledge layer that Jarvis and later agents retrieve from.

The MVP proves one complete vertical slice:

```text
source file
    ↓
discovery
    ↓
identity + provenance
    ↓
text extraction
    ↓
chunking
    ↓
search index
    ↓
retrieval
    ↓
agent-readable result with source evidence
```

If that path works reliably against real documents, the MVP succeeds.

**Revision note.** This replaces the first draft, which specified Obi-Wan as though nothing else existed. Jarvis is already running at Phase 1.5 and already holds a data model, a journal, a policy gate, and a full-text index. Section 1 supplies that context, section 3 records the decisions taken because of it, and embeddings have moved out of scope. Companion document: `COMMAND-STRUCTURE.md`, which defines who may operate what is built here.

---

## 1. Context: the system Obi-Wan joins

Obi-Wan is not a greenfield project. It is the third actor in a system that already runs.

**One LLM lives on this network and it is called Jarvis.** Obi-Wan does not get a model, does not call a model, and does not add an assistant to the LAN.

**What exists today**, in `HPZ440_LLM`, Phases 1 and 1.5 complete:

| Component | State |
|---|---|
| `llm-api` | llama.cpp serving one 7B instruct GGUF on an RTX 3060 |
| `jarvis` | The assistant: capture, classify, draft, chat, tools, teaching notes |
| `open-webui` | Browser chat against both backends |
| `jarvis/core/nko.py` | The Normalized Knowledge Object: immutable, versioned, layering facts, observations, classifications, recommendations and decisions beside one another |
| `jarvis/journal` | Append-only event log, one JSONL file per day |
| `jarvis/policy` | Permission gate enforced in code, not in prompts |
| `jarvis/retrieval` | SQLite FTS5 over the mail archive, rebuildable from the archive |
| `jarvis/sources/workspace` | Reads workstation documents on demand, archives nothing |

**The three roles**, defined fully in `COMMAND-STRUCTURE.md`:

```text
Conrad    commander-in-chief   decides, approves, forgets, amends powers
Jarvis    admiral              operates, captures, acts, commands sub-agents
Obi-Wan   historian            keeps the record, its provenance, its accuracy
```

**What Obi-Wan adds** that Jarvis does not have: durable file identity, scanning of file-shaped sources, chunking with position, a provenance model that distinguishes human from machine origin, and sole ownership of the record so that the actor cannot rewrite history.

**What Obi-Wan does not replace in v0.1.** Jarvis keeps its mail archive, its journal, its policy gate, and its notes. Migrating the mail archive behind Obi-Wan is later work, not this stage.

---

## 2. Goal

Given a bounded set of configured directories containing real text-bearing documents, Obi-Wan shall:

1. discover the files;
2. assign and retain durable file identity;
3. detect unchanged and changed content;
4. extract text deterministically;
5. divide extracted text into retrievable chunks;
6. build a search index over those chunks that can be destroyed and rebuilt from stored data;
7. retrieve relevant chunks for a query;
8. return enough provenance to identify the source of every result;
9. distinguish source-derived, human-created, and machine-created information; and
10. expose retrieval through an interface Jarvis uses.

The original files remain authoritative wherever they live.

Obi-Wan does not become the authoritative file store.

## 3. Decisions governing this MVP

| # | Decision | Consequence |
|---|---|---|
| 1 | Obi-Wan is the sole writer of the durable record | Jarvis submits and reads. It holds no UPDATE and no DELETE |
| 2 | Whoever holds the credential captures | Obi-Wan reads file sources itself, read-only. Jarvis submits what it captures from credentialed systems |
| 3 | Human origin carries an attestation rung | `relayed`, `direct`, and `attested` by one-time password in v2.0 |
| 4 | v0.1 implements two rungs | `relayed` and `direct`. v2.0 widens the check with nothing to backfill |
| 5 | Code lives in `HPZ440_LLM` | Obi-Wan is a service in the existing `compose.yaml`. The NKO model moves to a package both services import, and Obi-Wan owns its schema |
| 6 | v0.1 retrieval is full-text plus Jarvis's judgment | No embeddings, no encoder, no model call from Obi-Wan. The projection seam is reserved |
| 7 | The corpus starts local, with an inbox | Source roots are configuration. A NAS share is added later without code change |
| 8 | Obi-Wan may write only inside its own inbox | Every source root is mounted read-only |

Decision 6 is the change from the first draft. Measurement drove it: the only model on this network ranked an unrelated passage above the correct one on a retrieval probe, because a chat model is trained to continue text rather than to place related text near related text. Full-text search plus Jarvis reading the shortlist uses Jarvis for what it is genuinely good at, and costs no new model, no new container, and no re-embedding problem.

## 4. MVP scope

v0.1 operates against **explicitly configured source roots** plus **one inbox**.

It is not a whole-NAS crawler.

For each supported file, Obi-Wan records at minimum:

```text
file_id            Obi-Wan-generated, durable, minted once
current_location   where it was last seen
content_hash       the bytes of one observed version
file_size
modified_time
origin
first_seen_at
last_seen_at
```

`file_id` is identity. The current pathname is an attribute of the file, not its identity, because files move.

The content hash represents the bytes of a particular observed version. A new hash for the same `file_id` is a new version, not a new file.

For the bounded v0.1 corpus, files may be eagerly byte-hashed. NAS-scale optimization is explicitly deferred.

## 5. Documents and chunks

The primary knowledge structure for v0.1 is:

```text
DOCUMENT
    │
    ├── identity          file_id, version
    ├── location          current path
    ├── source metadata   size, mtime, media type
    ├── content hash
    ├── provenance        origin, attestation, timestamps
    └── extracted representation
             │
             ▼
           CHUNKS
             │
             ├── extracted text
             ├── document reference
             ├── position within document
             └── derived search representations
```

A chunk must never lose its relationship to its source document.

A retrieval result must therefore be traceable:

```text
result
  → chunk
      → document
          → source file
```

This is sufficient for v0.1.

A generalized claim or assertion graph is not.

---

## 6. Provenance

Every knowledge-bearing record must have an origin that the storage layer understands.

The v0.1 origin classes are:

```text
source
human
machine
```

### `source`

Information deterministically derived from an authoritative artifact, such as a document on disk. Re-running the extractor over the same bytes yields the same result.

### `human`

Information deliberately supplied by the Commander. Carries an attestation rung:

```text
relayed    Jarvis reports that you said it, unverified,
           carrying the conversation reference
direct     created through Obi-Wan's own confirm channel
           under your credential
attested   one-time password from your device   (v2.0)
```

### `machine`

Information created by a model, an agent, an automated extraction, or an inference process, when it is not merely a deterministic representation of source material.

**The rules the storage layer enforces.** Origin is derived from the authenticated caller, never read from the payload. The attestation rung is derived from the channel, never claimed by the caller. A machine writer cannot label its information `human`, and machine-generated information does not silently become human-confirmed information.

More detailed origin types may be added later without changing this distinction.

---

## 7. Machine knowledge

v0.1 stores a machine-generated note so that the architecture proves it can distinguish machine knowledge from source or human knowledge.

Machine knowledge remains machine knowledge.

v0.1 does **not** require:

- generalized approval workflows;
- multi-stage evidence promotion;
- confidence scoring;
- automated contradiction resolution;
- human review queues; or
- claim lifecycle management.

Those may be introduced when real use demonstrates their necessity.

---

## 8. Retrieval

The MVP must support a query equivalent to:

```text
What do we know about X?
```

The division of labour is deliberate:

```text
Obi-Wan   finds candidate chunks and hands them over
          with full provenance.   Finds. Does not judge.

Jarvis    reads the candidates and decides what they mean
          while composing an answer.   Judges.
```

Obi-Wan ranks by full-text relevance only. It never scores meaning with a model, because judging meaning is interpretation, and interpretation belongs to the actor. Anything Jarvis concludes re-enters the record as `machine`.

Retrieval must return agent-readable results containing at minimum:

```text
content
origin
attestation        (when origin is human)
file_id
document version
source location
chunk location
```

and enough additional identifiers to retrieve or inspect the underlying source.

Every response must also state **coverage**: documents indexed, chunks indexed, work pending, work failed. A partial index must never be able to look complete.

Results must not present machine-generated information as though it came from a source document or from the Commander.

Retrieval should be explainable at the level necessary to answer:

> Where did this result come from?

For v0.1 that is more important than sophisticated reasoning about:

> Why does Obi-Wan believe this is true?

The latter belongs to a future claim and evidence layer.

---

## 9. The search index is a disposable projection

The search index is derived data. It is never authoritative knowledge.

Deleting the entire index must not destroy the documents, extracted text, chunks, provenance, or identity information required to recreate it.

Rebuilding is therefore conceptually:

```text
discard projection
       ↓
rebuild projection from stored chunks
```

rather than migrating authoritative knowledge. No source file is re-read and no text is re-extracted to rebuild the index.

**The reserved seam.** Embeddings are out of scope for v0.1, but the schema reserves their table so that adding them later is additive rather than a migration:

```text
projection(
  chunk_id,
  kind,            'fts' today, 'vector' later
  model,           null for fts
  model_revision,  null for fts
  dimensions,      null for fts
  state,           pending | current | stale | failed
  reason,
  built_at
)
```

This table records projection **state**, not projection content. The searchable payload lives in the store belonging to its kind: the full-text virtual table today, a vector table later. One state table across all kinds gives coverage reporting a single source of truth and makes "which chunks are stale" answerable without consulting each index.

Any future projection, embedding or otherwise, must record how it was created, so that a model change marks rows `stale` rather than silently mixing incompatible data. That rule exists now even though only one projection kind is built.

---

## 10. Local-first operation

The v0.1 processing path is local and uses no model at all.

Source documents, extracted text, chunks, and queries must not leave the local environment merely because a component has a cloud fallback.

The default rule is:

> **No Obi-Wan content leaves the LAN unless the Commander explicitly enables an external provider.**

Obi-Wan holds no outbound credential of any kind: no mail, no internet egress, no write access to any source root, and no route published off the host.

Cloud integration is not required for MVP success.

---

## 11. Access model

v0.1 needs enough authorization to prove that the three roles are separable. `COMMAND-STRUCTURE.md` is authoritative; this is the subset v0.1 builds.

```text
reader     may retrieve
writer     may submit records with origin source or machine
commander  may create human-origin records at the direct rung,
           promote relayed to direct, and order forgetting
```

Jarvis holds the reader and writer credentials. It cannot reach the commander channel, and the confirm route refuses its credential even when it is relaying your instruction to confirm. That refusal is the reason the attestation ladder means anything.

Per-agent credentials, sub-agent scopes, and NAS-derived permissions are reserved, not built.

---

## 12. Idempotent ingestion

Running ingestion repeatedly against unchanged source roots must not create duplicate documents or duplicate chunks.

At minimum, ingestion must distinguish:

```text
new file
unchanged file
changed file
```

The documented move rule for v0.1: a file whose content hash matches a known `file_id` but whose path differs is treated as that same file moved, and only its `current_location` changes. Identity survives the move. Two files with identical content at two paths are recorded as two files, with the duplication noted rather than resolved.

The rule's known limit, stated so it is not discovered as a surprise: a file that is moved **and** edited between two scans matches neither its old path nor its old hash, so v0.1 records it as a new file and the old `file_id` is left pointing at a location that no longer resolves. Detecting that case needs identity the filesystem supplies rather than identity derived from path or bytes, which is deferred.

Perfect NAS-wide identity resolution is not required.

Failures must be visible rather than silently converted into successful records.

---

## 13. Fault tolerance and postponement

**Standing rule.** Work that cannot be completed because something it depends on is unavailable must be postponed durably, never dropped and never retried in a tight loop.

Nothing in v0.1 waits on Jarvis, because ingestion uses no model and full-text indexing needs none. The dependencies v0.1 must actually tolerate are:

| Dependency | Failure | Required behaviour |
|---|---|---|
| A source root | Unmounted, unreachable, or vanishing mid-scan | That root is skipped, its documents are left untouched, and the scan reports the gap. Nothing is marked deleted because a mount was absent |
| Extraction | Corrupt, encrypted, or unsupported file | A durable work row records the attempt count, last error, and next attempt. The inbox copy moves to `failed/` with the reason beside it |
| The service itself | Restart mid-scan | Claims carry a lease, so a reclaim path recovers work stranded in progress |

A chunk is never deleted because a later stage failed. A record never exists without the provenance that explains it.

This rule governs every later dependency by inheritance, including the embedding and enrichment work that decision 6 defers.

## 14. Interfaces

**Obi-Wan exposes:**

```text
POST /submit            writer credential.  origin forced to
                        source or machine.  human is refused
POST /relay             writer credential.  records the Commander's
                        words as human/relayed with conversation ref
POST /confirm           commander credential only.  promotes
                        relayed to direct.  also orders forgetting
GET  /search            reader credential.  candidates + provenance
                        + coverage
GET  /document/{id}     reader credential.  one document, versions,
                        provenance, chunks
GET  /status            reader credential.  roots, counts, pending,
                        failed, last scan
POST /scan              writer credential.  trigger a scan
POST /reindex           writer credential.  drop and rebuild the
                        projection from stored chunks
```

**Obi-Wan requires from Jarvis: nothing.** v0.1 needs no new service exposed from Jarvis, because Obi-Wan calls no model.

**Jarvis gains:**

```text
jarvis/obiwan_client.py        a client
policy actions                 obiwan_submit, obiwan_search
journal events                 one per submission and per search
tool  search_knowledge         so the Commander can ask in chat
```

## 15. Deliberately NOT in v0.1

The following are explicitly deferred:

- embeddings, encoders, and vector search;
- any model call made by Obi-Wan;
- migration of the Jarvis mail archive behind Obi-Wan;
- one-time-password attestation;
- whole-NAS crawling;
- millions-of-files optimization;
- filesystem journals and change feeds;
- NAS access-control synchronization;
- multiple scanner hosts;
- sub-agent scopes and per-agent credentials;
- knowledge graphs;
- ontologies;
- generalized assertions and claims;
- contradiction detection;
- temporal truth reasoning;
- automatic supersession;
- confidence calculus;
- machine-to-human promotion workflows;
- review dashboards;
- a web UI;
- distributed workers;
- message brokers;
- cloud processing;
- reranking models;
- a generalized plugin ecosystem;
- multi-user support; and
- premature scaling infrastructure.

Their absence is intentional.

They must not be added to v0.1 merely because a reference implementation contains them.

## 16. First corpus and the inbox

Two kinds of location, and the distinction is a safeguard rather than a convenience.

**Source roots** are read-only, always, enforced at the container mount. Files stay exactly where their owner put them. Obi-Wan reads and records; it never writes, moves, renames, or deletes.

**The inbox** is Obi-Wan's own staging ground. Work arrives there, and Obi-Wan may move files within it.

```text
/srv/obiwan/
  corpus/                 source root, read-only
  inbox/                  drop work here
    processed/2026-10-02/  recorded, moved aside
    failed/
      scan.pdf
      scan.pdf.error.json  why it failed
```

The inbox therefore always shows what is pending, which is what makes it a worklist rather than a second corpus.

The first corpus is seeded with real documents whose subject matter overlaps heavily, so that retrieval quality can be observed rather than assumed. The eleven research deliverables in this directory, plus `roadmap.md` and this document, serve that purpose and have known correct answers.

Adding a NAS share later is a configuration change to the list of source roots, with no code change.

Do not begin with the full NAS.

## 17. Required end-to-end demonstration

The MVP is successful when the following can be demonstrated from a clean installation.

### Ingest

Point Obi-Wan at the configured roots. It discovers, identifies, hashes, extracts, chunks, and indexes the supported documents.

### Re-ingest

Run ingestion again with nothing changed. No duplicate knowledge is created and no file is re-extracted.

### Change

Modify one source document and ingest again. Obi-Wan records a new version of the same `file_id` and does not confuse the new content with the previous version.

### Move

Rename or relocate one source document. Its `file_id` survives and only its location changes.

### Inbox

Drop a document into the inbox. It is recorded and moved to `processed/`. Drop a corrupt file. It moves to `failed/` with the reason beside it, and nothing partial reaches the record.

### Source unavailable

Make a source root unreachable and scan. That root is reported as a gap, its documents are untouched, nothing is marked deleted, and a later scan completes the work.

### Retrieve

Ask a question whose answer exists in the corpus. Obi-Wan returns candidates with coverage, Jarvis judges them, and the answer carries a resolvable path:

```text
answer
    ↓
chunk
    ↓
document version
    ↓
source file
```

### Machine write

Store one agent-generated note. Retrieve it. The result is unmistakably labelled `machine`, and the agent cannot cause the same record to be stored as `human`.

### Human write

Teach Obi-Wan one fact through Jarvis. It is recorded as `human` at the `relayed` rung. Confirm it through Obi-Wan's own channel and it becomes `direct`, with both the original rung and the promotion visible. Jarvis's credential is refused at that channel.

### Rebuild

Discard the search projection and rebuild it from stored chunks. Retrieval works again, with no source file re-read and no authoritative knowledge recreated by hand.

## 18. Definition of done

Obi-Wan v0.1 is DONE when:

- one bounded real document corpus can be ingested;
- unchanged re-ingestion is idempotent;
- changed documents are detected as new versions;
- moved documents keep their identity;
- documents have durable Obi-Wan identities;
- original source files remain authoritative and unwritten;
- extracted text is chunked and traceable to its source;
- the search index is explicitly derived and rebuildable from stored data;
- the projection table records how each projection was built, so a future model change marks rows stale rather than mixing incompatible data;
- retrieval returns useful results with stated coverage;
- every returned result identifies its origin;
- every source-derived result can be traced to a source document version;
- machine-created information cannot masquerade as human-created information;
- a human-origin record carries the attestation rung of the channel that created it, and only the Commander can promote it;
- work blocked by an unavailable dependency is postponed durably and visibly;
- Jarvis can retrieve through a defined interface, and Obi-Wan calls no model to serve it;
- the system runs locally without cloud processing; and
- the record can be destroyed and rebuilt during development without risking the source corpus.

When these conditions are met, **stop adding features and declare v0.1 complete.**

## 19. Implementation rule

Do not solve a deferred problem merely because its future solution is visible.

When implementation encounters an architectural question, ask:

```text
Does this prevent the v0.1 Definition of Done?
```

If **yes**, make the smallest reasonable decision and continue.

If **no**, record it for later and continue.

If the choice is cheap to reverse, choose a reasonable implementation and continue.

The next deliverable after this document is **working source code.**
